# Private HQ → Memex TLS bridge

Prepared assets only. Nothing here provisions certificates, deploys services, enables the HQ bridge, or approves memory automatically. Node22 is pinned to the same reviewed linux/amd64 base manifest as Memex; the image adds no dependencies. Archive the built image ID before deployment.

Topology: HQ → `https://memex-tls:3443/mcp` → fixed `http://memex:3000/mcp`. The proxy alone joins both the internal `oria-memex-tls-private` network and existing internal `oria-memory-private`. HQ joins only the TLS network in addition to its existing networks. No published ports. Check the existing external memory network is actually internal before deployment; Compose cannot enforce attributes on an external network. Provider runners must not join either memory network.

The proxy accepts POST `/mcp` with an `amh1` Bearer handle and two explicit operator routes: POST `/operator/review/snapshot` and POST `/operator/review/decision`, each requiring the separate `opr1` credential format. Credential families cannot cross these channels. Memex remains the authentication/scope authority; matching a format does not authenticate a caller. There is no publication route or arbitrary path forwarding.

It forwards only authorization/content-type/accept/content-length. One upstream attempt, no redirect, maximum1MiB response, 1MiB MCP request or16KiB operator request, deadline10seconds including client body and upstream response, maximum8 accepted in-flight requests, maximum32 TLS connections. MCP upstream errors/non2xx/redirects map to generic502. Operator status200/400/401/404/409/413/503 and bounded JSON bodies pass through so HQ can distinguish a conflict from an unknown outcome; other statuses map to502. Malformed or missing authorization gets401 at this proxy. No body/header/credential logging. TLS minimum1.2. Separate GET `/health` is loopback-only on3080 and proves liveness, not certificate validity or Memex access.

The operator additions are source changes pending separate deployment qualification. Do not infer that the currently deployed image includes them. The operator credential is scoped to one workspace and held only by Memex and the HQ backend, not the TLS proxy or agent runners. HQ must derive the human actor from its owner session; a client-supplied reviewer is not trusted. `deploy/hq-pilot/provision-memex-review.py` prepares separate externally owned files and never enables a service or overwrites an existing credential.

## Operator preparation (not executed by this task)

Review and run `provision-certificates.sh /absolute/new-private-directory` on the Linux operator host with OpenSSL and permission to chown the leaf key to UID1000. It refuses an existing directory. A new private CA signs a90-day server certificate with SAN `memex-tls`; its CA signing key remains operator-owned and must be retained offline, never mounted into either service. The script generates real secrets only when explicitly invoked by the operator. Compose file-backed secrets preserve host ownership; leaf key0400 UID1000 is intentional. Public certificates0444. Do not place this directory inside a repository or image context.

Set `MEMEX_TLS_KEY_FILE`, `MEMEX_TLS_CERT_FILE`, `MEMEX_TLS_CA_FILE` to absolute external paths. Set `MEMEX_HQ_HANDLE_DIRECTORY` to the dedicated external directory containing only the rotating read-only `handle` file. The root-owned rotation workflow is maintained separately: issue a one-hour handle every30minutes, atomic rename, permission readable by HQ's actual runtime UID. Mount the directory, not the file inode, so replacements remain visible. Never mount Memex's signing key into HQ or proxy. Remove any conflicting `MEMEX_HTTP_READ_HANDLE` environment value because HQ rejects simultaneous inline and file configuration.

Run `node deploy/memex-tls/check-static.mjs` and `node --test deploy/memex-tls/proxy.test.mjs`. Then review resolved Compose using `docker compose -f deploy/memex-tls/compose.json config --quiet`; do not dump runtime env files. Build/start only after deployment review. Apply HQ overlay together with its base Compose: `docker compose -f deploy/hq-pilot/compose.json -f deploy/memex-tls/hq.overlay.json config --quiet`. The overlay requires the new HQ image with the file-handle resolver. It sets CA trust, endpoint and handle path but intentionally does not enable the bridge or select a workspace. Exact workspace binding and activation are separate reviewed changes.

`NODE_EXTRA_CA_CERTS` is loaded at process startup: recreate HQ when changing its public CA. This expands trust for the HQ Node process, so the private CA must be dedicated and its signing key tightly controlled. Restart policy remains `no` as in existing pilots; agree on restart supervision before claiming durable operation. Monitor certificate expiry and handle rotation failure; no silent fallback or indefinite credential lifetime.

## Qualification and limits

Local tests pass with a temporary OpenSSL-generated synthetic certificate: correct CA/SAN succeeds to application401, unknown CA and wrong SAN fail TLS. HTTP tests exercise fixed upstream/minimal headers, rejection before upstream, redirects, oversized/truncated output, deadline, capacity release and eight-request concurrency. These are offline loopback tests, not production credentials or VPS integration. Temporary keys are removed after tests.

Before enabling: verify Docker network membership/internal flags/no ports and UID/read-only limits; validate actual HQ Node fetch trusts mounted CA and rejects wrong CA/SAN; exercise real HQ read factory with exact workspace canary, reject foreign/expired/tampered handles and writes, ensure no credential logging, and prove renewal without restart. Stop/restart proxy and Memex and repeat reads; confirm provider containers cannot connect. Liveness alone is insufficient. HTTPS ends at the proxy; the final hop remains confined to the existing internal Memex network. No certificate-validation bypass or HTTP allowlist relaxation is included.
